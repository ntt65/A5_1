# 미션 시작 프롬프트

아래 내용을 새 개발 채팅의 첫 프롬프트로 사용한다. 대괄호를 채우며, 모르는 값은 `미정`으로 둔다.

---

이 미션의 실행 구조를 설계하라. 대원칙은 ****토큰 이코노믹 분산계획****이다. 요구 품질과 완료 조건을 충족하면서 계획·구현·조정·통합 전체의 토큰 사용을 최소화하라. 분산 실행을 의무화하지 말고 단독 실행보다 경제적인 작업만 분산하라.

**운영 우선순위는 토큰 절약·누적 캐시 입력 절감·불필요한 재호출 방지다.** 아래 개발론은 이 원칙 안에서 미션에 필요한 수준만 적용한다. 이를 위해 필수 요구사항이나 정확성을 생략하지 말고, 중복 문맥·과도한 문서화·불필요한 단계·재작업을 줄인다. 캐시 적중 자체를 피하려고 안정된 입력을 바꾸지 않는다. 줄일 대상은 불필요하게 반복 사용하는 입력의 크기와 호출 횟수다.

## 입력

- 프로젝트 경로: [경로]

- 미션과 요구사항: [본문 또는 문서 경로]

- 저장소·기존 이슈: [주소 또는 미정]

- 실행·평가 환경: [환경 또는 미정]

- 브랜치·PR·통합 정책: [프로젝트 정책 또는 미정]

- 검증 담당·CI 성공 조건: [예: GitHub Actions에서 지정 환경 검사 / 미정]

- 전체 토큰 예산: [수치 또는 미정]

- 시간·비용·품질 제약: [조건 또는 미정]

- 승인 범위: 미션 분석과 아래 계획 문서·실행 프롬프트 작성. 코드 구현, 테스트 실행, 외부 이슈 생성, push·PR·머지, 설치·설정 변경은 포함하지 않는다.

## 1. 최소 문맥으로 미션 파악

현재 Git 상태, 전달된 지침, 미션, 관련 기존 구현·결과만 확인하라. 사용자 변경은 보존한다. 이미 제공된 내용과 확인한 자료는 다시 읽지 않는다. 전체 저장소·로그를 출력하지 말고 파일 목록과 관련 심벌·행부터 조회한다.

요구사항을 완료 조건에 연결하고, 기존에 충족된 항목과 실제 남은 작업을 구분하라. 계획에 필수적인 정보가 없을 때만 질문을 묶어서 요청하라. 미정 값은 추측해 사실로 기록하지 않는다.

## 2. 토큰 이코노믹 분산계획

다음 항목을 한 번의 통합된 계획으로 정리하라. 계획을 위한 계획이나 동일 내용의 문서 복제를 만들지 않는다.

- 공통 문맥: 모든 작업이 알아야 하는 요구사항·인터페이스만 짧게 정리한다.

- 개별 문맥: 작업마다 필요한 파일·심벌·선행 산출물만 지정한다.

- 실행 방식: 단독·순차·병렬 방식의 문맥 복제, 호출, 조정, 통합 비용을 비교해 선택한다. 작은 작업에는 별도 에이전트를 배치하지 않는다.

- 의존성: 선행 작업과 공통 인터페이스를 정하고, 독립 작업만 병렬 배치한다. 동일 파일의 수정 담당자를 명확히 하고 병렬 구현은 별도 worktree를 사용한다.

- 예산: 분석·계획·구현·통합과 필요한 실패 복구 여유분을 배분한다. 주담당·보조 에이전트·자동 검토의 사용량도 집계 범위에 포함하되 확인 불가분은 따로 표시한다.

- 호출 제한: 작업별 예상 호출 수와 상한, 재시도 조건과 상한을 정한다. 예상값은 추정으로 표시한다. 예산 미정이면 확정 예산처럼 쓰지 않는다.

- 종료 조건: 완료하면 추가 탐색을 중단한다. 한도 초과가 예상되거나 승인 범위를 벗어나면 상태·산출물을 보존하고 한 번 보고한 뒤 해당 작업을 멈춘다.

총 토큰은 캐시 입력 + 비캐시 입력 + 출력으로 계산한다. 추론 출력이 출력에 포함된 경우 다시 더하지 않는다. 캐시 포함 총량과 실제 과금은 구분한다. 시작·종료 누계, 세션 ID, 측정 시각을 남기고 서로 다른 세션의 누계를 빼지 않는다. 측정·차단 기능이 없는 실행 환경에서는 예산 준수를 보장한다고 주장하지 않는다.

## 3. 작성할 문서

아래 개발 절차를 문서와 실행 프롬프트에 반영한다. 작은 변경은 단계를 묶고, 해당하지 않는 항목은 이유와 함께 제외한다. 절차를 적는 것과 실제 실행 승인은 구분한다.

### 기본 개발 절차

- 요구사항: 기능·비기능 요구, 제약, 제외 범위, 사용자 관점의 인수 조건을 정의하고 작업 ID에 연결한다. 기존 구현을 재사용하며 완료된 기능을 다시 만들지 않는다.

- 설계: 필요한 구조·데이터 흐름·인터페이스·오류 처리·보안·호환성 영향을 정한다. 공통 계약을 먼저 확정하고 의존성·위험·대안을 짧게 기록한다.

- 구현: 하나의 목적에 필요한 코드·테스트·관련 문서를 작업 단위로 묶는다. 관련 없는 리팩터링·의존성 추가를 하지 않으며 변경 범위 확대는 승인받는다.

- 검증: 요구사항별 정상·경계·실패 조건과 필요한 단위·통합·인수 검증을 연결한다. 검증 환경·명령·성공 기준·담당을 미리 정하고 CI 위임 시 로컬에서 중복 실행하지 않는다. 변경 없는 통과 결과는 재사용하고 변경 영향이 있는 부분만 재검증한다.

- 완료·인계: 요구사항 충족 여부, 변경 파일·커밋, 검증 근거, 실행 방법, 알려진 제한을 전달한다. 구현 완료·CI 성공·통합 완료·배포 완료를 구분하고 미실행 단계를 완료로 표시하지 않는다.

### 소프트웨어 설계·프로그래밍 원칙

- 개발 방식: 작은 단위의 점진적 구현을 기본으로 하고 불확실성·위험이 큰 부분을 먼저 해결한다. 폭포수·애자일·TDD 등 특정 방법론을 일괄 강제하지 않는다. 계획 단계와 문서를 늘리기 전에 실제 오류·재작업 감소에 필요한지 판단한다.

- 요구사항 추적: 요구사항 ID → 작업 → 구현 위치 → 인수 조건·검증 근거를 미션 계획의 한 표로 연결한다. 같은 내용을 여러 문서·에이전트 프롬프트에 복제하지 않는다. 범위 변경은 영향과 추가 예산을 확인한 뒤 승인 범위에서 반영한다.

- 단순성: KISS·YAGNI에 따라 현재 요구를 충족하는 가장 단순한 설계를 선택한다. 사용하지 않을 확장점·계층·프레임워크를 만들지 않는다. DRY는 같은 지식·규칙의 중복에 적용하되, 우연히 비슷한 코드를 성급하게 추상화하지 않는다.

- 모듈화: 관심사 분리·정보 은닉·높은 응집도·낮은 결합도를 적용한다. 함수·모듈의 책임과 공개 인터페이스를 명확히 하고 핵심 로직과 외부 입출력을 필요한 만큼 분리한다. SOLID 등 객체지향 원칙은 해당 구조가 있는 경우에만 사용하며 원칙 적용을 위해 클래스를 늘리지 않는다.

- 데이터·알고리즘: 입력 규모와 연산 특성에 맞는 자료구조·알고리즘을 선택한다. 타입·단위·범위·불변조건·빈 값·경계값을 명시하고 중복된 상태를 줄인다. 성능 요구나 측정 근거 없이 조기 최적화하지 않는다.

- 계약·오류 처리: 입력 검증, 반환 형식, 실패 상태, 자원 해제를 정한다. 외부 호출에는 필요한 제한 시간·취소·재시도 상한을 두고, 재시도가 필요한 쓰기 작업은 중복 효과 방지를 설계한다. 오류를 숨기거나 무조건 재시도하지 않는다.

- 가독성·유지보수: 프로젝트의 명명·타입·서식 규칙을 따르고 주석에는 비자명한 이유·제약을 쓴다. 필요한 변경 범위 안에서만 리팩터링하며 기존 공개 계약과 데이터 호환성을 보존한다. 새로운 의존성은 필요성·유지 비용을 확인하고 승인 범위에서 추가한다.

- 품질 전략: 요구 동작을 기준으로 정상·경계·실패 사례를 선택한다. 구현을 그대로 복제한 테스트와 같은 동작의 중복 검증을 피한다. 외부 경계의 통합 검증과 핵심 사용자 흐름의 인수 검증을 필요한 만큼 계획하며 실행은 지정된 CI에 맡긴다. 작은 문서 변경에 기능 테스트를 추가하지 않는다.

- 보안·운영: 다루는 데이터와 기능에 맞춰 입력 경계·권한·비밀정보 보호를 고려한다. 네트워크·개인정보·영속 데이터·배포가 있는 경우에만 관련 로그·설정·마이그레이션·복구 조건을 구체화한다. 민감한 내용을 로그나 모델 입력에 불필요하게 포함하지 않는다.

- 적용 기록: 위 원칙을 각각 별도 조사·검토·모델 호출로 만들지 않는다. 선택한 구조와 중요한 절충만 기존 계획에 짧게 기록하고 작업 프롬프트에는 해당 작업에 필요한 결정만 전달한다.

### Git·CI·통합 절차

- 착수: 현재 브랜치·기준 SHA·사용자 변경·원격 주소를 확인한다. 원격 작업이 필요할 때 기존 인증 계정 선택과 권한을 확인하되 인증 비밀을 출력하거나 전역 설정을 임의 변경하지 않는다.

- 이슈·분리: 기존 이슈를 재사용하고 새 이슈는 승인된 경우에만 등록한다. 작업별 파일·선행 이슈·브랜치·worktree·담당자를 연결한다. 브랜치 흐름은 프로젝트 합의를 따르며 미정이면 계획 승인 때 확정한다.

- 커밋: 목적별 변경 파일 또는 hunk만 스테이징하고 실제 staged diff를 확인한다. Conventional Commits와 해당 이슈 번호를 사용하되 없는 번호를 만들지 않는다. 사용자 변경을 포함하지 않고 SHA와 잔여 변경을 기록한다.

- CI 설계: 기존 워크플로를 우선 재사용한다. 평가에 필요한 OS·런타임·의존성·명령·성공 조건만 정하고 불필요한 환경 조합을 추가하지 않는다. 검사 실패가 실패 종료 코드로 반영되도록 한다. push·PR 트리거와 필수 검사를 정하며 프로젝트 정책이 요구하지 않는 중복 실행은 줄인다.

- 병렬 결과 수집: 담당자는 변경 파일·기준 및 결과 SHA·검증 결과·미해결 사항만 인계한다. 통합 담당자가 의존 순서와 파일 충돌을 처리한다. 필요한 경우 통합용 브랜치에 모으고, 대상 브랜치의 보호 규칙과 필수 CI를 우회하지 않는다.

- 전달·머지: 승인된 브랜치를 push하고, PR이 필요한 흐름이면 승인된 대상에 PR을 생성한다. 실행 SHA·CI 실행 ID를 연결하고 완료를 기다린다. 필수 CI가 해당 SHA에서 성공하고 필요한 리뷰·승인이 충족된 경우에만 승인된 머지를 수행한다. develop → main 흐름은 합의된 프로젝트에서만 적용한다.

- 실패·복구: 실패한 job·step·관련 로그만 읽고 코드 실패와 인증·환경·서비스 실패를 구분한다. 수정된 입력 또는 확인된 일시 장애 근거 없이 같은 실행을 반복하지 않는다. 재시도 상한과 예산을 지키며 검증되지 않은 결과를 통합하지 않는다. 배포·데이터 변경이 포함된 미션은 복구 기준과 절차도 계획한다.

- 이력 보존: force push·reset·이력 재작성·브랜치 삭제는 명시적 승인 없이 하지 않는다. CI 또는 승인 대기는 실행 ID와 상태를 보존하고 반복 모델 호출 없이 처리한다.

| `plans/<mission-id>.md` | 요구사항별 작업·인수 조건, 의존성, 담당 파일·에이전트·브랜치·worktree, 기준 SHA, 예산·호출 상한, 검증 환경·명령·CI 성공 기준, 산출물, 프롬프트 목록 | 관계없는 과거 채팅·로그 전체 |

| `prompts/<mission-id>/` | 아래 단계별 실행 프롬프트와 재사용 가능한 작업 템플릿 | 작업마다 반복 복사한 전체 저장소·미션 문서 |

기존 파일이 있으면 먼저 필요한 부분만 확인하고 승인된 범위에서 갱신한다. 기존 정책을 임의로 삭제하거나 완화하지 않는다. 구체적인 미션 ID와 문서 경로는 한 번 정해 일관되게 사용한다. 이슈는 우선 로컬 작업 ID로 관리하며 외부 등록은 별도 승인이 있을 때만 한다.

## 4. 단계별 프롬프트를 미리 준비

미션 분석 후 전체 단계의 프롬프트 초안을 작성하라. 현재 확인할 수 있는 입력은 채우고, 선행 결과가 필요한 값은 명시적인 변수로 남긴다. 미래의 커밋 SHA·실행 결과·오류를 미리 만들어 넣지 않는다. 새로운 사실로 계획 변경이 필요하면 해당 부분만 수정한다.

`01-plan-approval.md`: 요구사항·설계·실행 방식·예산·대상 파일・Git 흐름·검증 계획을 제시한다. 구현·이슈 등록·push·PR·머지의 승인 범위를 한 번에 구분하고 승인 전 실행하지 않는다.

`02-dispatch.md`: 선행 조건을 충족한 승인 작업만 배분한다. 기준 SHA·브랜치·worktree·파일 소유권·공통 인터페이스와 필요한 자료만 전달한다.

`03-task-template.md`: 작업 ID, 요구사항, 담당 파일, 읽을 범위, 선행 산출물, 입출력 계약, 허용 행동, 예산·호출 상한, 검증 명령·담당, 완료 조건, 커밋·결과 보고 형식을 포함한다. 이 템플릿으로 작업별 프롬프트를 준비한다.

`04-integrate.md`: 변경 파일·커밋·검증 근거를 수집하고 의존 순서대로 통합한다. 충돌과 변경 영향 범위를 처리하고 대상 브랜치의 필수 CI 전 머지를 금지한다. 실패해도 전체 구현을 재시작하지 않는다.

`05-deliver.md`: 승인된 push·PR을 수행하고 SHA에 대응하는 CI 실행 ID·필수 검사를 확인한다. 완료 대기는 프로그램에 맡긴다. 실패 시 관련 로그와 수정 작업만 연결하고, 성공 후 필요한 리뷰와 승인이 충족되면 승인된 머지만 수행한다. CI 위임 시 로컬 테스트를 실행하지 않는다.

`06-result.md`: 요구사항별 완료 여부, 변경 SHA·파일, PR·CI 결과, 통합 상태, 실행 방법·제한, 미완료 항목, 단계별 사용량과 추정 대비 차이를 보고한다. 전체 실행 로그는 재출력하지 않는다.

`recovery-template.md`: 실제 실패 원인·영향 범위·기존 실행 ID·수정 내용·남은 예산을 입력받는다. 같은 조건의 반복 재시도를 금지하며 필요한 수정 범위만 처리한다.

각 프롬프트에는 ****입력 → 할 일 → 산출물 → 완료·중단 조건****을 명시한다. 해당 작업의 설계 계약·필수 품질 조건만 포함하고 위 개발론 전체를 반복 첨부하지 않는다. 독립적으로 실행할 수 있을 만큼 정보를 주되 전체 채팅을 인계하지 않는다. 프롬프트를 작성했다는 이유로 다음 단계를 자동 실행하지 않는다.

## 5. 실행 제어와 대기

- 승인 필요 시 대상·이유·승인 방법을 한 번 표시한다. 사용자 응답이 없다는 이유로 재승인 요청이나 상태 조회를 반복하지 않는다.

- 실행 요청은 한 번 제출하고 ID를 보존한다. 완료 이벤트를 우선하며, 지원되지 않으면 실행 프로그램이나 도구의 충분한 대기를 사용한다. 대기 상태 확인만을 위한 모델 호출을 반복하지 않는다.

- 승인·실행 상태는 프로그램이 저장·재개하도록 설계한다. 문서만 작성하고 프로그램적 차단을 구현했다고 보고하지 않는다.

- 같은 작업의 중복 실행, 짧은 폴링·sleep 반복, 변화 없는 재점검을 금지한다. 새로운 입력·실제 실패 원인의 수정·사용자 요청 없이 재실행하지 않는다.

- 상태 확인·Git 명령·결과 저장 등 정해진 처리는 실행 프로그램이 담당하고, 모델은 분석·설계·구현처럼 판단이 필요한 단계에 사용한다.
